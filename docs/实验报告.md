### 4. 三条证据线

#### 线 1｜程序输出为什么是 1

| 命令 | 原始输出 |
|---|---|
| `cat work/e5-01/evidence/program-output.txt` | `1` |
| `grep -n 'config.h' main.c` | `2:#include "config.h"` |
| `grep -n 'VALUE' config.h` | `1:#define VALUE 1` |

解释链：`main.c` 第 2 行包含 `config.h` → 宏 `VALUE` 展开为 `1` → 程序打印 `1`。因此 `config.h` 是**真实参与编译**的依赖，而 Makefile 未声明它。

#### 线 2｜声明侧（`make -p` 内部数据库）

| 项 | 值 |
|---|---|
| 声明原文 | `main.o: main.c unused.h` |
| `make-db.txt` 行号 | **1061** |
| 对应 `Makefile` 行 | 第 **6** 行 `main.o: main.c unused.h`，**文件为 `fixtures/md-rd/Makefile`**（容器内被拷为 `/evidence/Makefile`），不是仓库根目录的 `Makefile` |
| recipe 来源 | `make-db.txt:1085` → `#  recipe to execute (from 'Makefile', line 7):`，正文 `$(CC) -c main.c -o main.o` 在 Makefile **第 7 行** |
| `# Files` 段起始行 | 565（取值区间 565 起，`main.o` 条目在 1061） |

> 口径提醒：仓库根目录的 `Makefile` 是 E4 遗留的「一键命令」文件（`make build` / `make shell` / `make scan` 等，镜像名 `e4-buildchecker:<学号>`），**不含** `unused.h`；E5 的被测样例是 `fixtures/md-rd/Makefile`。报告与展示中引用「Makefile 第 6 行」时必须写明是后者，否则容易与根目录同名文件混淆。

`make-db.txt:1061` 之后的数据库记录（同一 `# Files` 段内）：

| 行号 | 内容 | 含义 |
|---|---|---|
| 1061 | `main.o: main.c unused.h` | 声明的先决条件集合 |
| 1062 | `#  Implicit rule search has not been done.` | 未走隐式规则搜索 |
| 1063 | `#  Implicit/static pattern stem: 'main'` | 该条目的 stem |
| 1064 | `#  Last modified 2026-10-24 08:44:32.67996225` | 目标 mtime |
| 1065–1066 | `#  File has been updated.` / `#  Successfully updated.` | 本条规则在本次构建中被执行 |
| 1067–1069 | `# automatic` / `# @ := main.o` | 自动变量 `$@` = `main.o` |
| 1070–1078 | `# * := main`、`# < := main.c`、`# + := main.c unused.h`、`# ^ := main.c unused.h` | 自动变量 `$*`（stem）、`$<`（首个先决）、`$+`/`$^`（先决条件全集），与第 1061 行声明集合**互证** |
| 1085 | `#  recipe to execute (from 'Makefile', line 7):` | 该规则 recipe 的正文来自样例 Makefile **第 7 行** `$(CC) -c main.c -o main.o` |

> 两个行号不要混：Makefile **第 6 行是声明行**（`main.o: main.c unused.h`，对应 `make-db.txt:1061`），**第 7 行是 recipe 正文**（对应 `make-db.txt:1085`）。GNU make 的数据库按「声明行 / 命令行」分别记录，`(from 'Makefile', line N)` 指的是命令行所在行。

| Makefile 行 | 内容 | `make-db.txt` 行 | 库内标记 |
|---|---|---|---|
| 4 | `app: main.o` | 609 | 声明 |
| 5 | `\t$(CC) main.o -o app` | 634 | `from 'Makefile', line 5` |
| 6 | `main.o: main.c unused.h` | 1061 | 声明 |
| 7 | `\t$(CC) -c main.c -o main.o` | 1085 | `from 'Makefile', line 7` |
| 9 | `\t./app` | 1058 | `from 'Makefile', line 9` |
| 11 | `\trm -f app main.o` | 828 | `from 'Makefile', line 11` |

再往下是该规则的 recipe 来源注释 `#  recipe to execute (from 'Makefile', line 7):`（`make-db.txt:1085`），`1078` 行的 `$^` 显示 `main.c unused.h`，与第 1061 行的声明集合完全一致。

#### 线 3｜实际侧与进程归属（验收重点）

`trace/` 下 7 个进程文件：`t.14 t.15 t.16 t.17 t.18 t.19 t.20`，pid → 程序映射：

| 文件 | execve 依据 | 进程 | 角色 |
|---|---|---|---|
| `t.14:1` | `execve("/usr/bin/make", ["make", "-p", "app"])` | make (14) | 顶层构建进程 |
| `t.15:1` | `execve("/usr/bin/cc", ["cc", "-c", "main.c", "-o", "main.o"])` | cc (15) | `main.o` 的 recipe |
| `t.16:1` | `execve(".../cc1", ["cc1", ..., "-o", "/tmp/cc2exnMS.s"])` | cc1 (16) | 编译前端 |
| `t.17:5` | `execve("/usr/bin/as", ["as", "--64", "-o", "main.o", "/tmp/cc2exnMS.s"])` | as (17) | 汇编器 |
| `t.18:1` | `execve("/usr/bin/cc", ["cc", "main.o", "-o", "app"])` | cc (18) | `app` 的 recipe |
| `t.19:1` | `execve(".../collect2", [...])` | collect2 (19) | 链接驱动 |
| `t.20:1` | `execve("/usr/bin/ld", ["/usr/bin/ld", ..., "main.o", ...])` | ld (20) | 链接器 |

父子关系由 `clone` 的返回值建立（父进程 trace 中的 `= <子 pid>`）：

| 父 | 证据 | 子 |
|---|---|---|
| make (14) | `t.14:55 clone(child_stack=..., flags=CLONE_VM\|CLONE_VFORK\|SIGCHLD) = 15` | cc (15) |
| make (14) | `t.14:66 clone(...) = 18` | cc (18) |
| cc (15) | `t.15:64 clone(...) = 16` | cc1 (16) |
| cc (15) | `t.15:84 clone(...) = 17` | as (17) |
| cc (18) | `t.18:129 clone(...) = 19` | collect2 (19) |
| collect2 (19) | `t.19:96 clone(...) = 20` | ld (20) |

归属链：

```
main.o
├─ 声明侧  make-db.txt:1061        main.o: main.c unused.h        ← Makefile 第 6 行
└─ 实际侧  进程归属（同一 recipe job）
    make(pid=14)                  t.14:1    execve("/usr/bin/make", ["make","-p","app"])
     ├─ clone=15                  t.14:55
     │   cc(pid=15)               t.15:1    execve("/usr/bin/cc", ["cc","-c","main.c","-o","main.o"])
     │    ├─ clone=16             t.15:64
     │    │   cc1(pid=16)         t.16:1    execve(".../cc1", [...,"main.c",...,"-o","/tmp/cc2exnMS.s"])
     │    │    └─ 读取 config.h   t.16:580  openat(AT_FDCWD,"config.h",O_RDONLY|O_NOCTTY) = 4   ← 成功打开
     │    └─ clone=17             t.15:84
     │        as(pid=17)          t.17:5    execve("/usr/bin/as", ["as","--64","-o","main.o",...])
     │         └─ 写出 main.o     t.17:23   openat(AT_FDCWD,"main.o",O_RDWR|O_CREAT|O_TRUNC,0666) = 3
     └─ clone=18                  t.14:66
         cc(pid=18)               t.18:1    execve("/usr/bin/cc", ["cc","main.o","-o","app"])
          └─ ... collect2(19) ── ld(20)     t.20:82  openat(AT_FDCWD,"main.o",O_RDONLY) = 7
```

**归属的关键判据**：`cc1`（读 `config.h`）与 `as`（写 `main.o`）**不是串行链**，而是 `cc(pid=15)` 为一个 recipe job **并行派生**的两个子进程（`t.15:64` 与 `t.15:84` 两条 clone 的父都是 15）。二者共同完成 `main.o` 这一个构建任务，因此 `config.h` 的读取归属于 `main.o` 目标，而不是任何独立目标。cc1 读入 `main.c` 与 `config.h`、写出汇编 `/tmp/cc2exnMS.s`，as 消费该汇编并产出 `main.o`。

`:= <fd>` 为成功（`= 4`、`= 3`）；`= -1 ENOENT` 只是路径探测，不算实际依赖。

### 5. 结论（MD / RD）

```
目标 main.o
  实际依赖（trace，项目目录内、成功的 O_RDONLY/O_NOCTTY 打开）：main.c（经 cc1 读入）、config.h
  声明依赖（make -p 的 # Files 段，make-db.txt:1061）：main.c、unused.h
  MD = config.h —— 实际读取、但未在 Makefile 第 6 行声明；
       证据：trace/t.16:580（cc1 成功 openat）+ make-db.txt:1061
  RD = unused.h —— 在本次构建配置与该 recipe job 下未被观察到读取；
       证据：make-db.txt:1061 声明了 unused.h；make 确实把它当先决条件检查存在性
             （trace/t.14:46 newfstatat(AT_FDCWD,"unused.h",{st_mode=S_IFREG|0644,st_size=43},0)=0），
             但 7 个进程文件中没有任何一次对 unused.h 的成功 openat（读取内容），
             即"声明被采纳、内容未被读取"
目标 app
  实际 main.o（ld 读取，t.20:82/83）/ 声明 main.o（make-db.txt:609 `app: main.o`）→ 一致，无错误
```

RD 的表述口径：不写「`unused.h` 是冗余依赖」（绝对化），写「在**本次构建配置**下未被观察到读取」——与 `fullcheck.py` 的 `scope` 字段口径一致，因为更换编译选项（如 `-include`、依赖生成）后该头文件可能被读取。

交给 E6 的 oracle：`main.o` 的 `MD = config.h`、`RD = unused.h`；`app` 无错误。E6 的 `findings.json` 必须正好这两条，多一条或少一条都算 E6 失败。

### 6. 与论文原型的差异

| 维度 | 论文（TSE / BuildChecker） | 本实验 |
|---|---|---|
| 跟踪手段 | 自研 ptrace 跟踪器 | `strace -ff -s 4096 -e trace=%file,%process` |
| 声明来源 | GNU Make 内部数据库 | `make -p` 的 `# Files` 段（`make-db.txt` 第 565 行起），跳过伪目标与未实例化的模式规则 |
| 比较范围 | 项目目录内文件 | 相同；`/usr/include`、`/tmp`、`/lib` 等系统路径一律不计入依赖错误 |
| 构建模型 | 多项目、含 CMake 等复杂构建系统 | **单 Make 进程、每个 recipe job 单一最终输出**；递归 Make 直接判 `UNSUPPORTED` |
| 规模与结论 | 30 项目 / 13,579 条报告 / 29 条误报 | 1 个教学样例 / 2 条精确错误（1 MD + 1 RD） |

本实验只验证了**单样例上的检测正确性**，未复现论文的规模、噪声率与加速比结论，不对其泛化能力作任何断言。

### 7. 二次对照采集

```bash
python3 scripts/lab_cloud.py e5 --out work/e5-02 --image course1020-buildchecker:241880617   # E5_SECOND_EXIT_CODE=0
```

`work/e5-02` 与 `work/e5-01` 的结论一致（`program-output=1`、`make-db.txt:1061`、`trace/t.16:580`、7 个进程文件 `t.14—t.20`）。

两次采集的 pid 分配与行号在本环境下完全相同，原因是同镜像、同 shell 脚本、同构建顺序下容器内 PID 依次分配。因此「trace 不可混用」的正确表述不是「pid 会变」，而是：**每份 trace 属于一次独立的采集批次，引用时必须指明批次目录**（`work/e5-01` 或 `work/e5-02`），不能把一份的行号与另一份的结论拼在一起；E5 的 trace 也不能作为 E6 的输入，`fullcheck.py` 会重新 `make clean` + strace 自行采集，E5 结论只作为 E6 的预期值。

### 目标故障（被测程序本身）

> 待 E6/E7 填写：构建失败（FAILED）、多输出任务（UNSUPPORTED）、运行超时（TIMED_OUT）三类场景的返回状态、触发方式与容器清理记录。
> 记录口径：故障场景下被测程序退出码为 `1`、而测试结果为 PASS，表示工具按预期识别了故障。

### 教学范围与不可泛化结论

- 本实验仅覆盖 **1 个教学样例**（`fixtures/md-rd`），结论为 **2 条精确错误**（1 条 MD + 1 条 RD），**未复现**论文的 30 个项目、13,579 条报告、29 条误报等规模结论，也未涉及性能加速比。
- 构建模型限定为 **单 Make 进程、每个 recipe job 单一最终输出**；递归 Make 与多输出任务直接判 `UNSUPPORTED`。
- `unused.h` 的 RD 结论限定在**本次构建配置**下；更换编译选项（如依赖生成、`-include`）后该头文件可能被读取。
