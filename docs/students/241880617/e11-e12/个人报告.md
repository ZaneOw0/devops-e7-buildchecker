### 1. 上下游输出/输入与字段映射

E11-A 把 BuildChecker 的全量检测结果接入 EChecker 的历史缓存，形成“全量建图 → 缓存对齐 → 目标提交只做增量”的链路。三处衔接的字段如下：

| 上游输出 | 版本 / 载体 | 下游输入 | 消费字段 | 消费前校验 |
|---|---|---|---|---|
| BuildChecker 基线全量 `full-check` | `schema_version=e11e12-1`，`full-check.json` | EChecker 历史缓存 | `artifact.sha256`、`commit`、`data.findings` | 报告 `commit` 必须等于请求的 `base` |
| 真 strace 图 `baseline-full/actual-graph.json` | E8–E10 图格式，`main.o`/`helper.o` 两个目标 | `baseline-cache.json` 的 `actual` | `(type, target, dependency)` 三元组 | `actual` 必须由真图投影得到，且与 `declared` 同目标集 |
| `baseline-full/make-db.txt`（`make -p`） | 文本 | 同上，作为声明图的旁证 | `main.o`/`helper.o` 的 recipe 与 prerequisite | 与 Makefile 现行 recipe 一致 |
| EChecker `incremental-check` | `schema_version=e11e12-1`，`incremental-check.json` | MDFixer（E12 阶段 `repair`） | `commit`、`data.findings`、`artifacts` | `check_envelope`（schema/kind/status/commit）+ `load_artifact` 内容哈希 |
| 增量报告正文 `incremental-report.json` | `schema_version=e8e10-1`，`profile=GCC_LOCAL_HEADERS_EXPLICIT_MAKE` | 人工核对 + 报告引用 | `key`、`actual`、`declared`、`findings`、`added/resolved/refreshed/reused` | 与 `target-full/findings.json` 的发现集合逐项相等（`normalized()` 不等即抛 `FINDINGS_MISMATCH`） |

关键点：缓存复用判定的 `key` 是**整项目级**的，由 `directives`（每个 `.c/.h` 中以 `#` 开头的行）、`recipes`（Makefile 的 recipe 行）、`flags`（`-O0`）、`compiler`（`gcc 14.2.0`）四段共同决定，而不是按单个 `.o` 决定——这直接决定了下面换提交实验里“全复用 / 全刷新”的结果。

### 3. 本人的代码修改

**（a）`labs/e11e12/vendor/draft/autobuild.py`：候选 Dockerfile 的 FROM 校验兼容 pinned digest**

原实现把 `FROM` 行的 `@sha256:…` 直接切掉后与原始行比较，当项目自带的 `Dockerfile.broken` 已经 pin 了 digest 时必然误判为“改了基础镜像 tag”，真实项目接入因此硬阻塞（详见“故障与处理”F5）。改为：原始行本身含 `@` 时按整行（含摘要）比较，否则回退到按 tag 比较。

```python
# 修改前
if original[0] != proposed[0].split("@", 1)[0]:
    raise Failure("Candidate changed the original base image tag")

# 修改后
expected_from = proposed[0] if "@" in original[0] else proposed[0].split("@", 1)[0]
if original[0] != expected_from:
    raise Failure("Candidate changed the original base image tag")
```

语义变化：pinned 场景下**摘要必须逐字不变**（比原来更严），未 pin 场景行为不变。

**（b）新增 `labs/e11e12/test_student_241880617.py`（3 个类 / 7 个用例）**

### 5. 换提交实验（自主任务 A：哪些刷新、哪些复用）

在固定样例仓库的副本 `data/swap-repo` 上依次追加两个提交，然后各自作为一次 `e11-a` 运行：

| 提交 | 内容 | 对 `key` 的影响 |
|---|---|---|
| C2 `e7447c8d61f7` | `helper.c` 末尾追加一行注释（仅函数体/注释，不动 `#` 行） | `directives`、`recipes`、`flags`、`compiler` 全部不变 |
| C3 `6ba0f27f9f28` | `helper.c` 顶部加 `#include "config.h"` | `directives["helper.c"]` 由 `[]` 变为 `['#include "config.h"']` |

| 提交对 | job_id | `reused` | `refreshed` | `added` | 发现集合 |
|---|---|---|---|---|---|
| C1→C2 `0319556…`→`e7447c8…` | `job-385d28b563b742d7b5e9b48756496a46` | `['main.o','helper.o']` | `[]` | `[]` | 与基线相同 3 条（`MISSING main.o→config.h`、`MISSING main.o→extra.h`、`REDUNDANT main.o→unused.h`） |
| C2→C3 `e7447c8…`→`6ba0f27f…` | `job-0e5eb3d342ef45eda5e387b3cbceb809` | `[]` | `['main.o','helper.o']` | `[["MISSING","helper.o","config.h"]]` | 3 条 + `MISSING helper.o→config.h` |

结论（可直接引用）：

1. 只改实现体、不动 `#` 行与 recipe 时，整个项目的对象全部命中历史缓存，`reused` 覆盖 `main.o` 和 `helper.o` 两个目标，不产生新发现（C1→C2）。
2. 一旦 `helper.c` 多了一个 `#include`，`key.directives` 改变，缓存**整组失效**：`main.o` 虽然没有改动也一起 `refreshed`，同时 `helper.o` 的真实依赖里多出 `config.h`，于是 `added` 出现一条新的 `MISSING`（C2→C3）。
3. 复用粒度是整项目 `key`，不是单个目标文件——这是本轨道“增量”的边界：宁可多刷，不漏检。

证据目录：`work/e11-a-swap-c2b/`、`work/e11-a-swap-c3b/`（各自含 `incremental-check.json` 与 `incremental-report.json`）。首次尝试 `work/e11-a-swap-c2/`、`work/e11-a-swap-c3/` 保留为失败证据（`INVALID_REQUEST`，见 F2）。
